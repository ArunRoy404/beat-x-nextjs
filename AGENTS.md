## Project Context
- Styling: Tailwind CSS
- colors: always follow the globals.css file for colors. never use hardcoded colors (no raw hex/rgba in component classNames or style props). if the color/token is not there then add it to globals.css first (as a `:root` variable, plus a matching `--color-*` entry under `@theme inline` for flat/opaque colors so it becomes a Tailwind class like `bg-your-token`; translucent/rgba/gradient tokens can stay `:root`-only and be consumed via `var()`, e.g. `bg-[var(--your-token)]`, matching how `--modal-header-bg`/`--search-bg` are already handled) and then reuse it from there — never duplicate the same raw value across files
- reusable UI: prefer small, focused, reusable components over duplicating the same UI markup across features. before writing new UI, check `src/components/shared` for something that already fits. if a piece of UI is needed by a second feature/page, promote it into `src/components/shared` instead of copy-pasting it
- Backend: separated/external API (not in this repo) — never assume a colocated backend
- State: Zustand (we use zustand for state management)
- Package manager: npm
- dummy data management: since there is no backend for now. save dummy data in src\dummyData and then use zustand store to manage dummy data.
- responsiveness, the style and color i will provide for pages and components use them always for large devices. and for mobile devices, you can use tailwind css responsive utility classes to make it responsive. and adjust the sizes, spaces, padding, margin, styles depending on the info i will provide.
- reusable components: always import component using @. and for classname prop use cn().
- use "use client" only where it needed. never use it in a component that never needs it.

## Data Fetching / API Integration Rules
- SSR-first: any page reading from a GET API must be server-rendered — in the page's Server Component, build a query client via `getQueryClient()`, call `queryClient.prefetchQuery({ queryKey, queryFn })`, then wrap the client template in `<HydrationBoundary state={dehydrate(queryClient)}>`. The client component consumes the exact same `queryKey` via a `useX()` hook (`useQuery`) so first paint already shows real data — no client-side loading spinner on first load.
- 1-minute revalidation everywhere: `NEXT_PUBLIC_REVALIDATE_TIME` in `.env.local` (currently `60`) is the single source of truth for cache freshness. It already drives `staleTime`/`gcTime`/`refetchInterval` globally via `src/lib/reactQuery/queryClient.js` — every query hook auto-refetches every 1 minute even if nothing calls the manual revalidate endpoint. Don't hardcode `60000`/`60` again in a hook; if a value needs to change, change the env var.
- Note on ISR vs. SSR for authenticated pages: do **not** add `export const revalidate = ...` to a page whose data fetch goes through `axiosPrivate` (i.e. reads the signed-in admin's session via `getServerSession`/`cookies()`) — Next.js already forces that page into fully dynamic rendering, so `revalidate` would be a no-op, and worse, Next's segment-config validator requires `revalidate` to be a static literal (`60`, not `env.revalidateTime` or any other computed expression) — a computed value there is a **hard production build failure** (`Invalid segment configuration export detected`), not just a warning. True static ISR only applies to pages that don't depend on the session; only add `revalidate` there, and only as a literal number. Either way, the 1-minute auto-refresh still happens client-side via React Query's `refetchInterval`.
- On-demand invalidation: `POST /api/revalidate` (`src/app/api/revalidate/route.js`, guarded by the `x-revalidate-secret` header matching `REVALIDATE_SECRET`) calls `revalidatePath` for every path in `src/lib/revalidate/isrPaths.js` (or an explicit `{ paths: [...] }` override in the request body).
- Mandatory checklist for every new SSR/ISR page — never skip this, the revalidate infra has to stay in sync with what actually ships: add the page's path to `src/lib/revalidate/isrPaths.js`, confirm its query has a `queryKeys` entry so `prefetchQuery`/`useX()` share the same key, and confirm the page prefetches + wraps children in `<HydrationBoundary>`. A page that reads live data but is missing from `isrPaths.js` will silently go stale past the 1-minute window whenever `/api/revalidate` is called for "everything" (no explicit `paths`), since that call only walks the registry.
- Hooks layout: one `services/<domain>/<name>Services.js` (plain async functions using `axiosPublic`/`axiosPrivate`, one per endpoint) + one `hooks/api/<domain>/use<Thing>.js` per endpoint (`useQuery` for GET, `useMutation` for write) — same split the `auth` domain already uses.
- Cut the cord on integration: the moment a module's API is wired up, delete that module's dummy data file and strip the corresponding Zustand list/CRUD state for it — Zustand is only for local UI state that has no reason to survive a page reload or be shareable (dialog open state, in-progress form fields) from then on, never a cache or mirror of API data.
- No fabricated data: never render a guessed/hardcoded fallback (`|| "Bangladesh"`, `|| 18`, `|| "Local"`, etc.) for a field the API left empty or missing. Show the real value, or a plain empty-state marker (`"-"`, an empty list, a "No data" message) — never a value that looks like real data but isn't.
- No client-side filter/search/sort/pagination once a module is API-backed: these must be sent as API params/query/body from the hook. If the given endpoint/Postman collection doesn't document a param for it yet, leave the control (search box, filter tabs, pagination) visible and wired to its own local UI state, but don't fake the behavior with local `.filter()`/`.slice()` — it stays visually present but non-functional until the endpoint actually supports it.
- Filter/search/page state lives in the URL, not Zustand: for any module whose filters/search/pagination actually hit real API params, read and write that state via `src/hooks/useUrlListParams.js` (wraps `useSearchParams`/`router.replace`) — never `useState`/Zustand for it. This makes the current view shareable/bookmarkable and lets the SSR page prefetch the exact page the URL asks for. Export a pure `buildXParams(raw)` helper in its own file, NOT the `"use client"` hook file (e.g. `buildAudioBooksParams` lives in `audioBooksParams.js`, not `useAudioBooks.js` — every export from a `"use client"` file becomes client-only, so a Server Component `page.jsx` can't call a helper colocated there) that turns raw `{status, genre, q, page}`-shaped strings into the real API params object — call the *same* helper from both the SSR `page.jsx` (`await searchParams`) and the client container (`useUrlListParams().get(...)`) so their query keys always match and hydration never shows a spinner, whatever's in the URL. Debounce the search input's own local `useState` before writing it to the URL, not the query itself. Skip this entirely for a module whose filters aren't real API params yet (e.g. users) — don't wire non-functional controls into the URL either.
- Keep it minimal: no speculative props, unused state, or dead branches for capabilities the current API doesn't support yet.

## Figma → Code Workflow
- Building a new screen from Figma is the default now (not screenshots): call `get_metadata` to locate/confirm the target node, then — after loading the mandatory `figma-design-to-code` skill (`skill://figma/figma-design-to-code/SKILL.md` if not offered as a slash skill) — call `get_design_context` on that node before writing any code.
- Treat the JSX/Tailwind `get_design_context` returns as reference only, never final code: adapt it to this project's stack, component conventions, and design tokens. Never paste it in verbatim.
- Reuse before you build: check `src/components/shared` and the relevant role's existing components/layouts for something that already fits before creating new equivalents from a Figma node.
- Asset fidelity: download the real icon/image assets via `download_assets` and commit them locally (`public/icons/<domain>/` for icons, `public/<domain>/images/` for photos/art) instead of approximating with an existing icon library or redrawing by hand — unless an existing project icon's glyph clearly already matches. Icons whose color must change with state (active/inactive, etc.) get transcribed into `currentColor` SVG React components (see `src/icons/DashboardIcons.jsx`); icons that are always a single fixed color per the design are just static `.svg` files rendered via `<img>`.
- New colors/gradients discovered in a Figma screen still go through the standard globals.css token rule above — never inline a raw hex/rgba just because it came from Figma.
- A new non-admin/artist role (e.g. `user`) follows the same architecture those two already established: `src/layouts/<Role>DashboardLayout/`, `src/navigationData/<role>DashboardNavigation.js` + `src/navigationStore/<role>DashboardNavigationStore.js`, `src/templates/<role>/...`, `src/components/<role>/...`, and — until that role has a real backend — `src/dummyData/<role>/...` + `src/zustandStore/<role>/...`. Only reuse an existing shared layout (like `CommonDashboardLayout`) across roles when the visual language actually matches; a genuinely different design gets its own layout family built from the same primitives/conventions rather than an overloaded prop surface.
