## Data Fetching / API Integration Rules
- SSR-first with Prefetching: any page reading from a GET API must be server-rendered. In the page's Server Component (`src/app/.../page.jsx`), obtain a query client via `getQueryClient()`, call `await queryClient.prefetchQuery({ queryKey, queryFn })`, and wrap the client template in `<HydrationBoundary state={dehydrate(queryClient)}>`. The client component consumes the exact same `queryKey` via its `useX()` hook (`useQuery`) so first paint displays server-rendered real data immediately with zero client-side loading spinners. Never add `"use client"` to `page.jsx`.
- 1-minute revalidation everywhere: `NEXT_PUBLIC_REVALIDATE_TIME` in `.env.local` (currently `60`) is the single source of truth for cache freshness. It already drives `staleTime`/`gcTime`/`refetchInterval` globally via `src/lib/reactQuery/queryClient.js` — every query hook auto-refetches every 1 minute even if nothing calls the manual revalidate endpoint. Don't hardcode `60000`/`60` again in a hook; if a value needs to change, change the env var.
- Note on ISR vs. SSR for authenticated pages: do **not** add `export const revalidate = ...` to a page whose data fetch goes through `axiosPrivate` (i.e. reads the signed-in admin's session via `getServerSession`/`cookies()`) — Next.js already forces that page into fully dynamic rendering, so `revalidate` would be a no-op, and worse, Next's segment-config validator requires `revalidate` to be a static literal (`60`, not `env.revalidateTime` or any other computed expression) — a computed value there is a **hard production build failure** (`Invalid segment configuration export detected`), not just a warning. True static ISR only applies to pages that don't depend on the session; only add `revalidate` there, and only as a literal number. Either way, the 1-minute auto-refresh still happens client-side via React Query's `refetchInterval`.
- On-demand invalidation: `POST /api/revalidate` (`src/app/api/revalidate/route.js`, guarded by the `x-revalidate-secret` header matching `REVALIDATE_SECRET`) calls `revalidatePath` for every path in `src/lib/revalidate/isrPaths.js` (or an explicit `{ paths: [...] }` override in the request body).
- Mandatory checklist for every new SSR/ISR page — never skip this, the revalidate infra has to stay in sync with what actually ships: add the page's path to `src/lib/revalidate/isrPaths.js`, confirm its query has a `queryKeys` entry in `src/lib/reactQuery/queryKeys.js` so `prefetchQuery`/`useX()` share the same key, and confirm the page prefetches + wraps children in `<HydrationBoundary>`. A page that reads live data but is missing from `isrPaths.js` will silently go stale past the 1-minute window whenever `/api/revalidate` is called for "everything" (no explicit `paths`), since that call only walks the registry.
- Organized Architecture & Layout:
  1. `services/<domain>/<name>Services.js`: Plain async functions using `axiosPublic`/`axiosPrivate` returning `res?.data?.data` (one function per endpoint).
  2. `hooks/api/<domain>/use<Thing>.js`: Custom TanStack Query hooks (`"use client"`) wrapping `useQuery` or `useMutation` and consuming `queryKeys.<domain>.<key>()`.
  3. `hooks/api/<domain>/<name>Params.js`: Pure helper function (`buildXParams(raw)`) to parse and sanitize URL search parameters into endpoint params. Must live in its own non-client file so Server Components (`page.jsx`) can import it without client-bundle errors.
  4. `lib/reactQuery/queryKeys.js`: Single source of truth for all query keys in the app.
- Mandatory Optional Chaining (`?.`): MUST ALWAYS use optional chaining (`?.`) on ALL API data properties across templates, components, cards, charts, and formatters (e.g. `data?.statCards?.totalUsers`, `item?.title`, `upload?.coverUrl`, `event?.venue`, `act?.message`). Never dereference nested API object properties directly or assume they are defined.
- Filter/search/page/time-range state lives in the URL for true SSR: for any module whose filters/search/pagination/time-range (e.g. `range=7d`, `30d`, `3m`, `6m`, `1y`) hit API parameters, read and write that state via `src/hooks/useUrlListParams.js` (wraps `useSearchParams`/`router.replace`) — never use `useState`/Zustand for it. This makes the view shareable/bookmarkable and lets the SSR Server Component (`page.jsx`) receive `searchParams` (`await searchParams`), run `buildXParams(rawParams)`, and prefetch the exact query key and parameters requested by the URL.
- Cut the cord on integration completely: the moment a module's API is wired up, DELETE that module's dummy data file (`src/dummyData/<domain>/...`) AND DELETE/STRIP the corresponding Zustand store (`src/zustandStore/<domain>/...`). Zustand is ONLY for local transient UI state (e.g., modal open state) — never a cache, duplicate state, or fallback mirror for API data.
- No fabricated data: never render a guessed/hardcoded fallback (`|| "Bangladesh"`, `|| 18`, `|| "Local"`, etc.) for a field the API left empty or missing. Show the real value, or a plain empty-state marker (`"-"`, an empty list, a "No data" message) — never a value that looks like real data but isn't.
- No client-side filter/search/sort/pagination once a module is API-backed: these must be sent as API params/query/body from the hook. If the given endpoint/Postman collection doesn't document a param for it yet, leave the control (search box, filter tabs, pagination) visible and wired to its own local UI state, but don't fake the behavior with local `.filter()`/`.slice()` — it stays visually present but non-functional until the endpoint actually supports it.
- Keep it minimal: no speculative props, unused state, or dead branches for capabilities the current API doesn't support yet.
- Preserving UI design blocks missing backend data (STRICT RULE): If a design block or component is present in the UI layout but the API response does not contain data or fields for it yet, DO NOT delete or remove the component code. Comment out the component in the component/template file for future integration when the backend API supports it.
- Strict UI Structure & Styling Preservation (STRICT RULE): Never alter or break existing UI components' structure, layout hierarchy, spacing, or styling during API integration. Maintain exact visual layout integrity and component design at all times.


## Figma → Code Workflow
- Building a new screen from Figma is the default now (not screenshots): call `get_metadata` to locate/confirm the target node, then — after loading the mandatory `figma-design-to-code` skill (`skill://figma/figma-design-to-code/SKILL.md` if not offered as a slash skill) — call `get_design_context` on that node before writing any code.
- Treat the JSX/Tailwind `get_design_context` returns as reference only, never final code: adapt it to this project's stack, component conventions, and design tokens. Never paste it in verbatim.
- Reuse before you build: check `src/components/shared` and the relevant role's existing components/layouts for something that already fits before creating new equivalents from a Figma node.
- Asset fidelity: download the real icon/image assets via `download_assets` and commit them locally (`public/icons/<domain>/` for icons, `public/<domain>/images/` for photos/art) instead of approximating with an existing icon library or redrawing by hand — unless an existing project icon's glyph clearly already matches. Icons whose color must change with state (active/inactive, etc.) get transcribed into `currentColor` SVG React components (see `src/icons/DashboardIcons.jsx`); icons that are always a single fixed color per the design are just static `.svg` files rendered via `<img>`.
- New colors/gradients discovered in a Figma screen still go through the standard globals.css token rule above — never inline a raw hex/rgba just because it came from Figma.
- A new non-admin/artist role (e.g. `user`) follows the same architecture those two already established: `src/layouts/<Role>DashboardLayout/`, `src/navigationData/<role>DashboardNavigation.js` + `src/navigationStore/<role>DashboardNavigationStore.js`, `src/templates/<role>/...`, `src/components/<role>/...`, and — until that role has a real backend — `src/dummyData/<role>/...` + `src/zustandStore/<role>/...`. Only reuse an existing shared layout (like `CommonDashboardLayout`) across roles when the visual language actually matches; a genuinely different design gets its own layout family built from the same primitives/conventions rather than an overloaded prop surface.
